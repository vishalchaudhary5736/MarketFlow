# E-Commerce Backend — Project Overview

## 1. What this project is

A backend for an e-commerce platform, built as a set of independent services (microservices) instead of one single application. Each business area — auth, cart, catalog, inventory, orders, payments, notifications, analytics — runs as its own service, fronted by a single API gateway.

## 2. Architecture

```
                         ┌──────────────────┐
        client  ───────► │   api-gateway    │
                         └──────────────────┘
                                  │
        ┌───────────┬────────────┼────────────┬───────────┐
        ▼           ▼            ▼             ▼           ▼
   auth-service  cart-service  catalog-service  order-service  ...
        │                         │
        ▼                         ▼
   ┌────────────┐          ┌─────────────┐
   │ Neon       │          │ Redis Cloud │  (cache)
   │ Postgres   │          └─────────────┘
   └────────────┘
```

Both Postgres and Redis are managed cloud services (Neon and Redis Cloud), not local Docker containers — see section 6.

- **api-gateway** — the single entry point clients talk to.
- **auth-service** — authentication/authorization (has its own Postgres database via Prisma).
- **cart-service** — shopping cart state.
- **catalog-service** — product catalog (currently the one service wired up to cache data in Redis).
- **inventory-service** — stock levels.
- **order-service** — order lifecycle.
- **payment-service** — payment processing.
- **notification-service** — emails/alerts.
- **analytics-service** — tracking/reporting.

Each service is a separate NestJS application with its own `main.ts`, module, controller, and service — it runs as its own process on its own port, so one service crashing doesn't take the others down.

## 3. Repo layout

```
apps/
  api-gateway/
    src/           → controller, service, module, main.ts (entry point)
    test/          → e2e tests
    tsconfig.app.json
  auth-service/    → same shape as above, plus prisma.service.ts (Postgres access)
  cart-service/
  catalog-service/   → also has CacheModule wired up (Redis)
  inventory-service/
  notification-service/
  order-service/
  payment-service/
  analytics-service/

prisma/
  schema.prisma       → data model definition (currently just the auth-service User table)
  migrations/          → committed SQL migration history, generated by Prisma

nest-cli.json       → tells Nest CLI about all 9 apps (monorepo mode)
package.json         → one shared dependency tree for all services
package-lock.json     → locked dependency versions (must stay in sync with package.json — `npm ci` fails otherwise)
tsconfig.json         → shared TypeScript compiler config
tsconfig.build.json   → build-time overrides (excludes tests)
.env / .env.example   → per-service config: ports, Redis, and Postgres connection details (see below)
Dockerfile             → builds any one service into a container image
docker-compose.yml     → runs all 9 services (Redis/Postgres are cloud services, not containers here)
.dockerignore          → keeps secrets/build junk out of images
```

**Why one `package.json` for 9 apps?** It's a Nest monorepo: shared dependencies and tooling, but each app still compiles and runs as its own separate process. This is a common middle ground — not a true fully-independent microservice setup (that would mean separate repos/`package.json` per service), but it gives process isolation without the overhead of managing 9 separate dependency trees.

## 4. Environment configuration

- **`.env`** — real local values, gitignored, never committed. Loaded into each service via `import 'dotenv/config'` at the top of its `main.ts`.
- **`.env.example`** — committed template with the same variable names so anyone cloning the repo knows what to set (`cp .env.example .env`).
- **Per-service ports** — each service reads its *own* port variable (`AUTH_SERVICE_PORT`, `CART_SERVICE_PORT`, etc.) instead of a shared generic `PORT`, so all 9 can run at the same time without colliding.
- **Redis variables:**
  - `REDIS_HOST` / `REDIS_PORT` — pointed at a managed **Redis Cloud** instance (no local Redis container in this repo).
  - `REDIS_TTL` — default cache expiry in **milliseconds** (e.g. `180000` = 3 minutes) applied to any cached value that doesn't specify its own TTL.
- **Postgres variables:**
  - `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` — credentials for the database (kept for reference/documentation even though there's no local Postgres container to auto-initialize with them anymore).
  - `POSTGRES_PORT` — Postgres's default port (`5432`), mostly informational now.
  - `DATABASE_URL` — the actual connection string Prisma reads, currently pointing at a managed **Neon** Postgres instance (`...neon.tech`, with `sslmode=require`).

## 5. TypeScript configuration

- `module`/`moduleResolution: "nodenext"` — modern, Node-accurate module resolution.
- `outDir: "./dist"` — compiled output location; each service's `tsconfig.app.json` narrows this further to `dist/apps/<service>`.
- Removed unused `baseUrl`/empty `paths` — there are no shared `libs/` or path aliases yet, so this was dead config. Can be reintroduced later if a shared `libs/` folder is added for cross-service DTOs/utils.
- Fixed all 9 generated e2e test files: switched `import * as request from 'supertest'` to `import request from 'supertest'`, since namespace imports aren't callable under `nodenext`'s stricter module rules.

## 6. Docker setup

**Redis and Postgres are cloud services (Redis Cloud, Neon), not local containers.** Earlier drafts ran `redis`/`postgres` as containers in `docker-compose.yml`; both were removed once real cloud connection strings were in place, since every service already reads its config purely from environment variables (`REDIS_HOST`, `DATABASE_URL`, etc.) with no code assuming local vs. cloud. That's the payoff of driving config through `.env` — swapping infrastructure only touched `docker-compose.yml`, nothing else.

- **`Dockerfile`** — one multi-stage build shared by all services:
  1. `base` — installs only `package.json`/`package-lock.json` first (for build caching).
  2. `dependencies` — installs full deps (incl. dev tools needed to compile).
  3. `build` — copies source in, conditionally runs `prisma generate` **only when `SERVICE_NAME` is `auth-service`** (see below), then runs `nest build <service>` for whichever service is being built (`ARG SERVICE_NAME`).
  4. `production` — fresh image: copies in the `prisma/` folder, installs prod-only deps, runs the same conditional `prisma generate` again (a fresh `npm ci` here means a fresh, ungenerated client), then copies in just the compiled `dist/` output. No TypeScript, no test files, no source in the final image.
- **`docker-compose.yml`** — defines all 9 app services, each built from the same `Dockerfile` with a different `SERVICE_NAME` build arg, each getting its config from `.env` via `env_file`, each exposed on its own port, all sharing one Docker network (`ecommerce-net`) so they can reach each other by service name.
- **`.dockerignore`** — excludes `node_modules`, `dist`, `.git`, and `.env` from what gets copied into the image during build, so secrets and build artifacts never end up baked into an image layer. This only affects what goes *into the image*; `env_file` in `docker-compose.yml` is a separate, runtime-only mechanism that injects `.env` values into the running container — the two don't conflict.

**Gotcha #1 hit and fixed:** `@prisma/client` normally auto-generates itself via a `postinstall` hook when `npm install`/`npm ci` runs — but in the `dependencies` stage, `npm ci` runs *before* `prisma/schema.prisma` is even copied into the image (only `package.json` is copied that early, for build caching). So the auto-generation silently found no schema and produced nothing, and `nest build` later failed with `Module '"@prisma/client"' has no exported member 'User'`. Fixed by explicitly running `prisma generate` after the schema file is present.

**Gotcha #2 hit and fixed:** the first fix made `prisma generate` run unconditionally for **every** service's build — including `cart-service`, `payment-service`, etc., which have nothing to do with Postgres. Every one of those builds then failed with `Missing required environment variable: DATABASE_URL`, because `.env` (correctly) never reaches the build stage at all (excluded by `.dockerignore`), and `prisma generate` still validates that the env var exists even though it never actually connects to a database. Fixed two ways at once:
  - Wrapped the generate step in a shell conditional so it **only runs for `auth-service`**: `if [ "$SERVICE_NAME" = "auth-service" ]; then ... fi` — other services' builds no longer need to know or care about Postgres at all.
  - Supplied a **placeholder** `DATABASE_URL` (`postgresql://user:password@localhost:5432/placeholder`) inline just for that one command, since `prisma generate` only reads the schema to produce code and never opens a real connection. This avoids baking the real Neon password into the image's build history — the real `DATABASE_URL` only ever exists at container *runtime*, supplied by `docker-compose.yml`'s `env_file`.

## 7. Redis caching

Added to reduce repeated work for data that doesn't need to be fetched fresh every single request.

**Packages:** `@nestjs/cache-manager`, `cache-manager`, `keyv`, `@keyv/redis`.

**How the pieces fit together:**
```
your code → cache.get()/cache.set()   (Nest's CACHE_MANAGER token)
                    ↓
              cache-manager           (Nest's caching engine, storage-agnostic)
                    ↓
                 Keyv                 (generic key-value storage interface)
                    ↓
              @keyv/redis             (the Redis-specific adapter/implementation)
                    ↓
                 Redis
```
`cache-manager` doesn't know how to talk to Redis directly — it delegates to Keyv, which defines one common interface many different backends can implement (Redis, SQLite, Mongo, etc). This means swapping the storage backend later only touches the one `createKeyv(...)` line, not every place that calls `cache.get`/`cache.set`.

**Where it's wired up** — [apps/catalog-service/src/catalog-service.module.ts](apps/catalog-service/src/catalog-service.module.ts):
```ts
CacheModule.registerAsync({
  isGlobal: true,
  useFactory: () => ({
    stores: [createKeyv(`redis://${process.env.REDIS_HOST}:${process.env.REDIS_PORT}`)],
    ttl: Number(process.env.REDIS_TTL),
  }),
}),
```

**Where it's used** — [apps/catalog-service/src/catalog-service.service.ts](apps/catalog-service/src/catalog-service.service.ts), using the standard cache-aside pattern: check the cache first, and only compute/fetch and store the value if it wasn't already cached.
```ts
constructor(@Inject(CACHE_MANAGER) private readonly cache: Cache) {}

async getHello(): Promise<string> {
  const cached = await this.cache.get<string>('hello');
  if (cached) return `${cached} (from cache)`;
  const value = 'Hello World!';
  await this.cache.set('hello', value);
  return value;
}
```

**TTL behavior:** the `ttl` set in `CacheModule.registerAsync` (from `REDIS_TTL`) is only a *default*. Passing a TTL directly to a specific `cache.set(key, value, ttl)` call overrides the default for that key — the more specific value always wins. This lets different cached items expire on different schedules (e.g. fast-changing cart data vs. slower-changing catalog data) without changing the global default.

**Verified working end-to-end:**
```
curl localhost:3003/  → "Hello World!"               (cache miss, value written to Redis)
curl localhost:3003/  → "Hello World! (from cache)"   (cache hit, served from Redis)
redis-cli KEYS '*'    → "hello"                        (confirmed the key exists in Redis)
```

**Currently only wired into `catalog-service`.** To add caching to another service, copy the same `CacheModule.registerAsync(...)` block into that service's module and inject `CACHE_MANAGER` where needed — no `docker-compose.yml` changes required now that Redis is a cloud service reachable the same way from every container.

## 8. PostgreSQL + Prisma

Added so `auth-service` has somewhere durable to store real data (starting with user accounts), instead of everything living only in memory.

**ORM choice — Prisma over TypeORM:** picked as the more modern, widely-used option for someone new to SQL/Postgres — type-safe generated client, simpler migration workflow, better error messages, than hand-writing SQL or wrangling TypeORM's decorator/repository API.

**Packages:** `prisma` (the CLI — schema management, migrations, client generation) and `@prisma/client` (the actual client your code imports at runtime, generated to match the schema).

**Version gotcha hit and fixed:** `npm install prisma @prisma/client` pulled in **8.0.0-rc.15** — npm's `latest` tag currently points at an unreleased release candidate with a totally different, cloud-platform-oriented CLI (no `migrate dev`, no `generate` in the classic sense). Explicitly pinned both packages to **6.19.3**, the last stable release using the standard, well-documented Prisma workflow that matches virtually all tutorials and docs. Lesson: always sanity-check `npx <tool> --version` after installing when a package's `latest` tag seems newer than expected — `npm view <pkg> dist-tags` shows what `latest` actually resolves to.

**Schema** — [prisma/schema.prisma](prisma/schema.prisma):
```prisma
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User {
  id        String   @id @default(uuid())
  email     String   @unique
  password  String
  createdAt DateTime @default(now())
}
```
One `prisma/schema.prisma` at the repo root for now (not per-service) since only `auth-service` uses a database so far — kept simple rather than pre-building a multi-schema structure nothing needs yet.

**Editor tooling gotcha:** hovering `url` in `schema.prisma` shows a deprecation warning ("no longer supported... move to `prisma.config.ts`"). This is **not real** for this project — the actual installed CLI is pinned to 6.19.3 (confirmed via `npx prisma --version`), which still requires `url` in the schema. The warning comes from the editor's Prisma extension running a newer language server (targeting Prisma 7/8's config rewrite) than the CLI version actually in use. Accepting an editor "quick fix" for this once actually deleted the `url` line and broke `prisma generate` for real — restored it. Leave `url = env("DATABASE_URL")` in place as long as this project stays on Prisma 6.x.

**User uniqueness rules (current):** the same person may hold one account per role (e.g. a CUSTOMER and a SELLER account with the same email or phone), so nothing in `User` is unique on its own except `id`:
```prisma
@@unique([email, role])                      // one account per email per role
@@unique([countryCode, mobileNumber, role])  // one account per phone per role
```
Consequences for code:
- `findUnique` must use the compound keys: `where: { email_role: { email, role } }` or `where: { countryCode_mobileNumber_role: { countryCode, mobileNumber, role } }`. `where: { email }` alone no longer compiles.
- `findFirst`/`findMany` by email or phone still compile, but should also filter by `role`, otherwise they may match another role's account.
- `countryCode` and `mobileNumber` are nullable. Postgres treats `NULL`s as distinct, so rows without a phone never conflict, but a row with a `mobileNumber` and a `NULL` `countryCode` escapes the uniqueness check. The DTOs always require both together.

**Client wrapper** — [apps/auth-service/src/prisma.service.ts](apps/auth-service/src/prisma.service.ts):
```ts
@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit, OnModuleDestroy {
  async onModuleInit() { await this.$connect(); }
  async onModuleDestroy() { await this.$disconnect(); }
}
```
`PrismaService` *is* the database client (it extends `PrismaClient`), just made injectable through Nest's DI and hooked into the app's lifecycle so it connects on startup and disconnects cleanly on shutdown.

**Used in** [apps/auth-service/src/auth-service.service.ts](apps/auth-service/src/auth-service.service.ts) via two new endpoints on `auth-service`:
- `POST /users` — creates a user (`prisma.user.create(...)`).
- `GET /users` — lists all users (`prisma.user.findMany()`).

**Migrations:** `npx prisma migrate dev --name init` created `prisma/migrations/<timestamp>_init/migration.sql` (committed to git — this is the database's version-controlled change history) and applied it to Postgres, creating the `User` table.

**Verified working end-to-end, both locally and in Docker:**
```
POST localhost:3001/users {"email":"test@example.com",...}  → 201, user row returned with generated id
GET  localhost:3001/users                                    → array containing that user
```
Originally verified against a local `postgres` container; the database has since moved to Neon (see section 6) — same verification applies since `auth-service` only ever talks to whatever `DATABASE_URL` points at.

**Currently only wired into `auth-service`.** Each service that needs its own data should get its own Postgres database (a core microservice principle — see the very first question this project overview started from). When adding a database to another service, the pattern to repeat: give it its own `DATABASE_URL` (a separate Neon database/branch, or any other Postgres instance), extend `schema.prisma` (or give that service its own schema file) with its models, add a `PrismaService`-equivalent, and add the conditional `prisma generate` branch for that service in the `Dockerfile`.

## 9. How to run it

**Without Docker (local dev, one service at a time):**
```bash
npm install
npm run start:dev            # runs the default app (api-gateway)
nest start auth-service --watch   # run a specific service
```

**With Docker (all 9 services; Redis/Postgres are reached over the internet as cloud services):**
```bash
docker compose up --build     # build images + start all containers
docker compose up -d --build  # same, but detached (background)
docker compose logs -f        # tail logs
docker compose ps             # check which containers are running
docker compose down           # stop and remove everything
```

24. Added **`POST /auth/refresh`**, which exchanges the httpOnly refresh-token cookie for a new access token. Before this, `cookie-parser` had been installed and wired into `main.ts` by hand, and `login` / `verify-otp` had been changed to set a `refreshToken` cookie.
    - **Request:** no body. The browser sends the `refreshToken` cookie (it is scoped to `path: /auth`). The frontend must call with `credentials: 'include'` / `withCredentials: true`.
    - **Success (200):** `{ success: true, message: 'Session refreshed.', data: { accessToken } }`, plus a **new** `refreshToken` cookie (rotation).
    - **Failures (all 401, `action: 'SIGN_IN'`, and the cookie is cleared):** `REFRESH_TOKEN_MISSING` (no cookie), `REFRESH_TOKEN_INVALID` (bad signature, expired, or an old-format token), `SESSION_EXPIRED` (session gone from Redis, or user deleted), `REFRESH_TOKEN_REUSED` (an already-rotated token was replayed: treated as theft, so the whole session is deleted). A blocked or deleted account gives the usual 403 `ACCOUNT_SUSPENDED` / 410 `ACCOUNT_CLOSED`, also with the cookie cleared.
    - **Refresh token payload** changed from `{ sub }` to `{ sub, sessionId, jti }` (`RefreshTokenPayload` in [shared.types.ts](apps/auth-service/src/shared/shared.types.ts)). Without `sessionId` a refresh token could not be matched to or revoked with its session. `jti` is random, so a rotated token never equals the old one. **Refresh tokens issued before this change get `REFRESH_TOKEN_INVALID`; users sign in once more.**
    - **Tokens are now hashed in Redis:** `cacheSession` in [shared.service.ts](apps/auth-service/src/shared/shared.service.ts) stores SHA-256 of the access and refresh tokens (the fields were already named `tokenHash` / `refreshTokenHash` but held the raw tokens). `refreshTokenMatches()` compares hashes in constant time. Nothing else read those fields, so nothing broke.
    - **Cookie options in one place** in [auth.service.ts](apps/auth-service/src/auth/auth.service.ts): `refreshCookieOptions()` (`httpOnly`, `secure` in production, `sameSite: 'strict'`, `path: '/auth'`) plus `setRefreshCookie()`. The `res.cookie(...)` calls in `login` and `verifyOtp` now use it, so set and clear always match (a mismatch leaves the old cookie in the browser).
    - [main.ts](apps/auth-service/src/main.ts): added `credentials: true` to CORS. Without it the browser on `http://localhost:5173` neither stores nor sends the cookie.
    - Verified with real HTTP requests through the actual controller, `AuthService`, `SharedService`, `JwtService`, `cookie-parser`, interceptor and exception filter, with in-memory Redis/Prisma fakes. Results: Redis holds 64-char hashes, not tokens. No cookie, garbage, and old-format tokens give 401 with the cookie cleared. A valid cookie gives 200 with a new access token and a new, different cookie (`HttpOnly; SameSite=Strict; Path=/auth; Max-Age=604800`). The second refresh with the new cookie works. Replaying the first cookie gives `REFRESH_TOKEN_REUSED` and deletes the session, after which the newest cookie also gives `SESSION_EXPIRED`.
    - Known limits / follow-ups:
        - `login` and `verify-otp` **still also return `refreshToken` in the JSON body**. Any script on the page can read that, which undoes the point of the httpOnly cookie.
        - Two tabs refreshing at the same moment with the same cookie: the slower one looks like reuse and ends the session. The frontend should share one in-flight refresh call.
        - No `/auth/logout` yet (`LogoutDto` exists but no endpoint).
